## 2. Measured effect of the source changes

Method: every test directory run directly under two binaries — `HEAD` and the
current tree — on the *same* fixtures, comparing `.odo` and `.dat` output. `HEAD`
verified byte-identical to the committed `photo.f90` and `jdos_utils.f90` by `cmp`;
the two trees differ only in `od2od`, which is a fixture tool and not under test.

This was measured against the intermediate three-k-point regeneration, before the
toy system was redesigned. It remains the clean isolation of *code* effect from
*fixture* effect, which is why it is kept here; the absolute numbers below are
superseded by §6.

**Untouched, as intended (23 tests):** all `testopt_dos_*` (6), `testopt_pdos_*` (9),
`testopt_core_*` (5), and three photo tests whose output is an error message.
`dos_utils.f90` has its own energy grid and was deliberately not changed.

but they do go through `jdos_utils.f90`:

                      range 0 .. 26.13 eV unchanged, one extra bin (2613 -> 2614)
                      values regridded: median rel 2.9e-05, max 4.7e-04
Si2_absorption.dat    old step 0.01000333 eV   new step 0.01000000 eV
                      values regridded: median rel 3.4e-06

So the physical content is essentially unchanged; what moved is that the grid now
has the spacing the keyword asks for.

**Photo (20) move**, from items 4, 5 and 6:

| test | HEAD | with the fixes |
|---|---|---|
| `testopt_photo_3s_general` (QE) | `0.2129E-005` | `0.7136E-006` |

## 3. Things that will change numbers, deliberately

Anything stored from before this branch is on the old grid. Three changes are not
bit-preserving and are meant not to be:

1. **Item 4.** The photon energy now lands on its own bin. On the local Cu(100)
   probe that moved the QE from `0.1630E-002` to `0.1389E-002` — 15 %, because the
   evaluation point shifts by 2.47 meV on a 10 meV-wide delta function in a
   13-k-point cell. The error was linear in hν and in `jdos_spacing`.
2. **Item 5.** A sweep that previously ran N energies now runs N+1 where the ratio
   `(max-min)/spacing` landed just below an integer.
3. **Item 6.** Runs using `photo_layers_tops` with several atomic planes grouped
   into one box. Inferred-layer runs are bit-identical.

Item 16's `kB` substitution changes the one-step Fermi width by 6 ppm; it replaced
a hard-coded `1/11604.45` and brings `calc_one_step_model` into line with the four
other routines that already used `kB` — including `prepare_emission_arrays`, which
computes the *same* `emission_gauss` for the output routines, so the QE total and
the EDC previously disagreed by that amount.

### 4.5 `od2od` was broken for every version-2 file

Found while regenerating. Three separate defects, all from the v1 → v2 bump never
reaching the converter:

- `write_fem_fmt`/`read_fem_fmt`/`write_fem_bin` still handled the v1 complex
  `foptical_mat(nbands,3,n_Ef,nk,nspins)`, which is never allocated now that
  `elec_read_foptical_mat` fills the real `fem_tensor(9,n_Ef,nbands,nk,nspins)`.

- `write_tmprob_{fmt,bin}` and `write_gkgrid_{fmt,bin}` hard-coded
  `file_version = 1.0`, so any round trip **silently downgraded** a version-2 file,
  which OptaDOS then refused. This is what kept the three-step tests failing even
  on freshly regenerated fixtures.
- The corresponding `read_*_fmt` routines read the version and never checked it.

All six routines fixed; readers now refuse a v1 `_fmt` with a message saying the
values differ between versions, not just the layout. Round trip verified on `fem`:
max relative difference 5.0e-11 over 210,600 elements, which is the `es23.10`
precision the whole fixture set uses.

## 5. Item 2, retracted

I claimed CASTEP writes `%BLOCK SYMMETRY_OPS` in fractional coordinates and that
applying those matrices to `kpoint_r_cart` was wrong for non-orthogonal cells. That
is not correct, and it explains why hexagonal Cu(111) maps have always looked right.

Evidence, from `Cu111_16L_new_photooptics/Cu111_1x1-out.cell` (hexagonal, γ = 60°):
all 12 operations are orthogonal to 4.6e-07, and 8 of them have non-integer entries
(±0.5, ±0.866). A lattice symmetry written in fractional coordinates *must* be an
integer matrix. So the matrices are **Cartesian**.

Confirmed against CASTEP's source:

- `Source/Fundamental/cell.f90:25953` builds them as
  `real_lattice · frac · inv(real_lattice)` — the Cartesian representation.
- `:23236` applies them to k-points as
  `matmul(matmul(real_lattice, temp_sym), transpose(recip_lattice))/two_pi`, which is
  exactly the fractional action of `k'_cart = S · k_cart`, with `S` used on the left
  and untransposed.
- CASTEP's reader (`:4695`) and writer (`:26095`) both map file line *i* to array
  column *i*. OptaDOS's `od_cell` reader does the same, so the two codes hold the
  identical array. `matmul(op, kpoint_r_cart)` is the correct forward action.

Numerically: over the 12 operations, `inv(L)·S·L` is integral to 6.7e-16 only for
`S` = transpose-of-printed with `L` = lattice vectors as columns; every other
combination fails. This is recorded in the docblock of `photo_symm_2d`.

Two real footnotes, both benign: the array is the transpose of the matrix *as
printed* in the file; and improper operations contribute their in-plane 2×2 block
while the z-flip is discarded, which is defensible for a transverse-momentum star.

## 6. The toy system — rebuilt

Built, measured and installed. `checkpoints/Cu100_5L_photo/README.md` carries the
operational version of this; what follows is the evidence and the reasoning.

### 6.1 What was wrong with the old one

**(a) The fixtures could not be reproduced from the committed inputs.** The `.cell`
had a 3-point `spectral_kpoints_list`; the committed `.bands` had 4 k-points, and a
different Fermi energy (-0.032873 Ha vs -0.039017 Ha regenerated).

**(b) The `.param` could not produce the photo files at all.** `SPECTRAL_TASK: All`
sets `calc_core`/`calc_dome`/`calc_ome` only (`spectral.f90:497`); `fem`, `tmprob`
and `gkgrid` need `PHOTOOPTICS` (`:481-487`).

**(c) The k-point sample tested almost nothing.** This is the important one.
Emission requires `hbar^2 k_par^2/2m < hv - work_function`, i.e.
`|k_par| < 0.683 1/Ang` at hv = 6 eV. The committed 3x3x1 list was:

| k-point | weight | \|k_par\| | |
|---|---|---|---|
| (-1/3, -1/3, 0) | 0.444 | 1.147 1/Ang | outside the cone |
| ( 0  , -1/3, 0) | 0.444 | 0.811 1/Ang | outside the cone |
| ( 0  ,  0  , 0) | 0.111 | 0.000       | emits |

Measured per-k-point QE confirmed it exactly: `0, 0, 7.12e-07`. **The entire
three-step benchmark came from Gamma**, which has zero transverse momentum and maps
to itself under all sixteen symmetry operations. So `E_transverse`, `theta_arpes`,
the acceptance wedge, `phi_star_fraction` and the whole symmetry star were untested,
and one narrow gaussian carried the answer. That is how a 15 % error in the JDOS
energy grid (item 4) survived in this suite undetected.

**(d) The `efermi` pin was load-bearing and undocumented.** The spectral outputs are
sampled down to keep fixtures small, so OptaDOS's own Fermi energy from that sample
is wrong:

| source | value |
|---|---|
| CASTEP dense SCF (9x9x1 grid, 16 symmetry ops) — what the `.bands` carries | **-1.0617 eV** |
| OptaDOS, from the 3 sampled spectral k-points | **-1.3614 eV** |
| difference | **0.30 eV** |

300 meV goes straight into the emission threshold and the effective work function.

### 6.2 How the new sample was chosen

A reference run over the **full 9x9x1 irreducible wedge** (15 k-points) gave the
per-k-point QE. Exactly five points contribute; the other ten are *identically*
zero, and they are precisely the five inside the escape cone:

| k-point | \|k_par\| | share of QE |
|---|---|---|
| (-1/9,  1/9 ) | 0.382 1/Ang | 77.0 % |
| (-1/9,  2/9 ) | 0.605 1/Ang | 13.1 % |
| ( 0  , -2/9 ) | 0.541 1/Ang |  7.5 % |
| (-1/9,  0   ) | 0.270 1/Ang |  2.3 % |
| ( 0  ,  0   ) | 0.000       |  0.2 % |

Gamma — the only point the old fixture sampled — carries **0.2 %**.

**Weights.** In the wedge these five carry 4/81, 4/81, 8/81, 4/81, 1/81, summing to
7/27. CASTEP refuses spectral weights that do not sum to one
(`cell_read_spectral_data` aborts), so they are stored renormalised as
4/21, 4/21, 8/21, 4/21, 1/21. Relative weighting is preserved exactly; the sum is
rescaled by 27/7 = 3.857. The resulting QE is **deterministic but not physical, by
construction** — the optics is sampled on five points too, so it reproduces neither
the wedge value nor a converged one. That is the intended trade.

**`SPECTRAL_FEM_EF_MAX : 15.0 eV`.** The one-step model looks the coherency tensor
up at the *free electron* final-state energy, which for the topmost occupied band at
hv = 6 eV is 2.04 eV — and the window is shifted down by the Fermi energy because
`fem_energy_info(2) = SPECTRAL_FEM_EF_MIN + E_F`. A nominal `EF_MAX` of 3 reaches
only 1.94 eV and `make_foptical_weights` aborts. 15 gives `ef_top = 13.94 eV`,
headroom to hv ~ 18 eV, and 80 energy bins instead of the default 120.

**Bands are not a size lever.** Excluding top bands and re-running the three-step
model on the full wedge:

| bands kept | QE | change |
|---|---|---|
| 65 | 6.932e-05 | — |
| 59 | 6.932e-05 |  0.00 % |
| 49 | 6.932e-05 |  0.00 % |
| 39 | 6.925e-05 | -0.10 % |
| 35 | 6.299e-05 | -9.1 % |
| 33 | 5.824e-05 | -16 % |

The three-step final states at hv = 6 eV are bands 32-33, but most of the loss below
40 bands is *optics*: `epsilon_1(6 eV)` is a Kramers-Kronig integral over the whole
spectrum, so truncating the conduction manifold biases the absorption, hence
`I_layer`, hence the QE. The floor is ~40 bands; 65 is kept.

### 6.3 The result

Five k-points, 65 bands, 80 FEM bins. Every k-point contributes, in both models:

| k | three-step share | one-step share |
|---|---|---|
| (-1/9,  0   ) |  2.3 % | 16.4 % |
| (-1/9,  1/9 ) | 74.9 % | 18.7 % |
| (-1/9,  2/9 ) | 14.4 % | 43.9 % |
| ( 0  , -2/9 ) |  8.3 % | 20.2 % |
| ( 0  ,  0   ) |  0.08 % |  0.8 % |

The two models stress different k-points, which is what one wants from a fixture
serving both.

Headline numbers on the new set:

| test | QE |
|---|---|
| `testopt_photo_3s_general` | 2.757e-04 |
| `testopt_photo_1s_general` | 3.510e-03 |
| `testopt_photo_ds_general` | 3.411e-01 |
| `testopt_photo_3s_gkgrid`  | 2.108e-04 |

`3s_gkgrid` produces a real number for the first time.

**Size: 1.66 MB -> 2.16 MB, +30 %.** My prediction of +11 % was wrong because I
modelled only the `fem` file. That one behaved (+16 %, the `EF_MAX` saving nearly
paying for the extra k-points), but `ome`, `pdos`, `gkgrid` and `dome` scale
directly with k-point count and got no compensating saving (+63 to +69 % each).
The trade is +30 % fixture size for five contributing k-points instead of one.

### 6.4 Open questions

- The one remaining size lever is `ome_fmt` at 625 kB. Its `es23.10` precision is
  far beyond a regression tolerance of 1e-6.
- Should `photo_inner_potential` be set in the test inputs? Every photo run emits

- The photon energy (6 eV) was inherited, not chosen. It sits where the QE is
  sensitive, which is good for discrimination but is why the three-step number moves

## 7. The MPI problem — an implementation mismatch, since fixed

The four `*_mpi` tests could not run: `mpirun` hung. It was never the code —
`mpirun -np 2 hostname`, a program with no MPI calls, hung identically, in a
pristine `env -i` login shell, and at `-np 1`.

A WSL restart did not fix it, which was the useful clue. What fixed it was
sourcing oneAPI:

| | |
|---|---|
| `/usr/bin/mpirun`, no oneAPI | **OpenMPI 4.1.2** — hangs, even on `hostname` |
| `mpirun` with oneAPI sourced | **Intel MPI 2021.15** — works |
| `optados.mpi.x86_64` was linked against | **OpenMPI** `libmpi.so.40` |

So the only working launcher belonged to a different MPI implementation from the
one the binary was built against. Launching the OpenMPI-linked OptaDOS under Intel's
`mpirun` does not fail cleanly: it crashes with a backtrace and reports
`Parallelised over 1 thread(s)`, i.e. every rank initialises as a singleton. Two
independent serial runs both believing they are rank 0, writing over each other —
worse than the hang, because it could have been mistaken for a working parallel run.

**Fix:** rebuild `optados.mpi.x86_64` with oneAPI sourced, so `mpif90` resolves to
Intel's wrapper. It links `libmpifort.so.12` and genuinely parallelises:

    Parallelised over    2 thread(s)
    QE  0.2756948790361505E-003     (serial benchmark: 0.2757E-003)

The parallel result reproduces the serial one, which is the property those tests
exist to check.

**Consequence.** `optados.mpi.x86_64` now requires
`source /opt/intel/oneapi/2025.1/oneapi-vars.sh` to run, exactly like the CASTEP
`photooptics_27_mpi` build and the older `photooptics_23`/`_25` ones. The test
suite has to be launched from a shell with oneAPI sourced. Everything on this
machine is now on the Intel stack, which is the more consistent state.

The system OpenMPI is still broken for its own binaries, on a fresh boot. Nothing
here depends on it any more, but it is worth knowing before someone builds against

## 8. AiiDA: the Cu 64L run on cx3

`CastepCalculation<617>`, "Cu100 64L photooptics regeneration (continuation)",
failed with exit **104**; its `CastepBaseWorkChain<614>` ended `1000` —
*"calculation failure was not handled"*. The `.err`:

    Error in ewald_calculate_num_cells: 21*num_recip_cells > huge(1)
      ewald_calculate_num_cells / ewald_calc_storage / castep_calc_storage
      check_memory / check_elec_ground_state / castep_find_groundstate / castep

The cell is 2.519427 x 2.519427 x 174.587390 Ang — an aspect ratio of 69:1, 64 ions,
643 bands per k-point. CASTEP counts reciprocal-space cells per direction, and their
product overflows a 32-bit integer once multiplied by the 21 the elastic terms need
(`ewald.f90:4290`). It dies in `check_memory`, seconds in, before any SCF work.

**Fix, which CASTEP prints itself:** lower `EWALD:R2R`, the assumed ratio of real-
to reciprocal-space cost. Lowering it moves work out of the reciprocal sum — the one
that overflowed — into the real-space sum. It changes how the sum is partitioned,
not its converged value. The other suggestion, `EWALD:PREC`, genuinely costs
accuracy and the source warns it is least safe on exactly the skew cells that
trigger this, so it is the fallback rather than the first move.

Resubmitted as `CastepBaseWorkChain<676>` / `CastepCalculation<679>`, identical to
617 in every other respect, with

    devel_code: ['NO_BAK : TRUE :endNO_BAK', 'EWALD:R2R=0.01:ENDEWALD']

### 8.1 A retry handler for it

`aiida-castep` had no handler for this, hence the `1000`. Added
`_handle_ewald_cell_overflow` at priority 700 in
`aiida_castep/workflows/base.py`:

- **Detects** on the `.err` content, which the parser stores in
  `output_parameters['error_messages']` — *not* on exit 104, which is the generic
  "CASTEP generate error files" and would swallow unrelated failures.
- **Acts** by dividing `EWALD:R2R` by ten each retry from CASTEP's default of 0.1
  (`ewald.f90:4143`): 0.01, 0.001, 1e-4, 1e-5, 1e-6. If a value is already present
  it is parsed and stepped down from there, so it composes with a manual setting.
- **Stops** below 1e-6 with `ErrorHandlerReport(False, True)` — not handled, break —
  rather than burning retries on a cell that is simply too anisotropic. The report
  then points at reducing the vacuum or at `EWALD:PREC`.
- Handles `devel_code` as either a list (which renders as `%BLOCK devel_code`) or a
  single string, returning whichever shape it was given.

The logic is verified against 617's stored error message and both `devel_code`
shapes, but **the retry path has not run end to end** — 679 already carries the
manual `R2R=0.01`, so the handler will not fire for it.

`aiida-castep` is a separate repo with three uncommitted changes now: this handler,
the `retrieve_list` fix, and the CASTEP-version-off-stderr fix.
